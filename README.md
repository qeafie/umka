# Умка

**Удобный мобильный коммунальный ассистент.** Умка помогает жителям разобраться с бытовыми ситуациями, сохранить показания счётчиков и подготовить обращение в УК или ТСЖ.

Сейчас доступны инструкции по аварийным ситуациям, подготовка текста обращения, вход с проверкой данных запуска MAX, личный журнал счётчиков и пилотный сценарий общей проблемы дома. Сообщения об инцидентах сохраняются в Умке и видны участникам привязанного дома; они не отправляются в УК. Показания сохраняются только в Умке и не отправляются поставщикам. Официальный MAX-запуск требует токена бота и подключения приложения на платформе.

**Основной сценарий пилота:** житель открывает в MAX список проблем своего дома, сообщает о неисправности либо присоединяется к активной проблеме того же типа и участка. Диспетчер этого дома видит тексты сообщений, жители — только общую сводку. Диспетчер записывает исполнителя, следующий шаг и срок обновления, отмечает завершение работ. Жители отдельно подтверждают восстановление. Карта показывает ответы по подъездам и этажам, включая участки без свежих данных. Имя исполнителя пока является текстовым полем, отдельного кабинета исполнителя нет.

## Стек

- Laravel 13, PHP 8.4, Inertia 3.
- Vue 3 (Composition API, JavaScript), Tailwind CSS 4, Vite 8.
- Laravel Sail / Docker Compose, PostgreSQL 18, Node.js 24.
- PHPUnit 12 и Vitest 4 / Vue Test Utils. Тестовая БД — SQLite в памяти.

Версии зависимостей зафиксированы в `composer.lock` и `package-lock.json`.

## Запуск одной командой

Нужны Git, Bash и запущенный Docker с Docker Compose v2. Локальные PHP, Composer и Node.js не обязательны. На первом запуске нужен интернет для загрузки образов и пакетов.

```bash
git clone https://github.com/qeafie/umka.git
cd umka
./bin/setup
```

`./bin/setup` создаёт `.env`, устанавливает Composer-зависимости через Docker, собирает и запускает Sail / PostgreSQL, генерирует ключ приложения, применяет миграции, устанавливает npm-зависимости, собирает фронтенд и подключает Git hooks. При повторном запуске существующий ключ и данные сохраняются. Пароль БД из примера предназначен только для локального окружения.

Откройте [http://localhost:8000](http://localhost:8000). Должны появиться название «Умка» и домашние сценарии. [http://localhost:8000/up](http://localhost:8000/up) должен вернуть HTTP 200.

### Заполнение тестовыми данными

После миграций выполните локально:

```bash
./vendor/bin/sail artisan db:seed
```

`DatabaseSeeder` добавляет синтетический дом, двух жителей, диспетчера, администратора дома, одну общую проблему с двумя сообщениями и личный пример счётчика только в окружениях `local` и `testing`. Повторный запуск не создаёт дубликаты. Адрес, участники, показания и сообщения вымышлены; это не подключения к УК или поставщикам.

В `.env.example` для демонстрационных пользователей указаны фиктивные MAX ID. Чтобы войти в мини-приложение под тестовыми MAX-аккаунтами, задайте `UMKA_DEMO_RESIDENT_MAX_ID`, `UMKA_DEMO_NEIGHBOR_MAX_ID`, `UMKA_DEMO_DISPATCHER_MAX_ID` и `UMKA_DEMO_HOUSE_ADMIN_MAX_ID` равными ID подготовленных тестовых пользователей MAX и задайте `MAX_BOT_TOKEN` в локальном `.env`. Токен нельзя записывать в Git. Вход по паролю для этих записей не предусмотрен.

### Проверка карты дома

1. После заполнения тестовыми данными войдите через MAX как администратор дома и откройте «Проблемы в доме» → «Настроить схему дома».
2. Проверьте два подъезда по пять этажей. Демонстрационные жители привязаны ко второму и четвёртому этажам второго подъезда; это явно заданные данные, они не вычисляются из номера квартиры.
3. Под аккаунтом жителя отправьте ответ о состоянии услуги. Под аккаунтом диспетчера снова откройте список проблем: на карте появится свежий ответ. Нажатие на этаж раскрывает сводку без имён и номеров квартир.
4. Диспетчер отмечает завершение работ, жители отвечают на проверку восстановления. Молчание и устаревшие ответы не считаются подтверждением. Повторение того же ответа обновляет его время без двойного подсчёта.
5. После смены подъезда или этажа участник должен ответить снова: прошлый ответ не подтверждает состояние нового места.

Карта считает подключённых участников, а не все квартиры дома. На этапе проверки восстановления учитываются только участники, сообщившие об этой проблеме. Без настроенной схемы или привязки ответы не превращаются в выдуманные этажи. Уведомления и адресные опросы MAX требуют отдельной настройки бота, webhook и планировщика (см. ниже). Чтобы обновить карту, повторно откройте список проблем.

В разделе «Проблемы в доме» администратору также доступна кнопка «Управлять участниками». Здесь можно назначить существующему участнику роль жителя, диспетчера или модератора и отозвать доступ после подтверждения. Изменения действуют только в выбранном доме и записываются в журнал; сообщения участника сохраняются. Собственную роль и доступ изменить нельзя. Приглашение новых участников и назначение администраторов через этот экран пока недоступны.

## Разработка

После первоначальной настройки:

```bash
./vendor/bin/sail up -d
./vendor/bin/sail npm run dev
```

Vite работает в текущем терминале. Остановить его можно через `Ctrl+C`. Для работы без Vite выполните `./vendor/bin/sail npm run build`.

```bash
./vendor/bin/sail down
```

Эта команда останавливает окружение, сохраняя БД. Повторный запуск — `./vendor/bin/sail up -d`. Не добавляйте `-v`, если данные нужно сохранить: этот флаг удаляет тома.

## TDD и проверки

1. Написать тест нового поведения.
2. Запустить его и убедиться, что он падает по ожидаемой причине.
3. Написать минимальную реализацию.
4. Получить зелёные тесты, затем рефакторить.
5. Проверить полный набор перед коммитом и после него.

```bash
./bin/test
./vendor/bin/sail artisan test --filter=HomePageTest
./vendor/bin/sail npm run test:watch
./vendor/bin/sail composer lint:check
./vendor/bin/sail npm run build
```

Если PHP 8.4+ и Node.js 24 установлены локально, после установки зависимостей доступен `./bin/test --local`.

Backend-тесты проверяют страницы и навигацию Inertia, подпись запуска MAX, сессии, доступ к счётчикам и домам, изоляцию данных, создание и группировку проблем, роли диспетчера, а также повторный запуск сидера. Vue-тесты проверяют основные сценарии, загрузку и интерфейсные состояния. Тестовая БД не использует локальную PostgreSQL.

Для получения токена чат-бота задайте `MAX_BOT_TOKEN` в `.env`. Ключ инициализации MAX проверяется на сервере по [официальному алгоритму подписи](https://dev.max.ru/docs/webapps/validation). Для промоматериалов доступны [логотип](public/brand/umka-logo.svg), [знак](public/brand/umka-mark.svg) и [маскот](public/brand/umka-mascot.svg); описание бренда — в [docs/brand.md](docs/brand.md).

Перед внешней проверкой его нужно заменить на публичный HTTPS-адрес, подключить MAX-бота и подготовить реальные тестовые аккаунты MAX. ## Git

Работать только в отдельных ветках, например `feature/add-incidents`. Сообщения коммитов короткие: `Инициализация проекта`.

```bash
git config core.hooksPath .githooks
git switch -c feature/add-incidents
```

`pre-commit` запрещает коммиты в `main` / `master` и detached HEAD. `post-commit` запускает PHP- и Vue-тесты в Sail после каждого коммита. Поэтому контейнеры должны работать. Post-commit не отменяет уже созданный коммит: при ошибке исправьте проблему до push. После нового клонирования hooks нужно подключить через `./bin/setup` или указанную команду.

GitHub Actions запускает тесты, проверку форматирования PHP и сборку фронтенда на push и pull request. Защита основной ветки на GitHub настраивается отдельно владельцем репозитория.

## Архитектура и данные

`routes/web.php` → Inertia middleware → `resources/js/pages/Home.vue`. Единственный сервер Laravel и единственная БД PostgreSQL. Зависимости npm в Docker хранятся отдельно от хостовых, чтобы не смешивать нативные пакеты macOS и Linux.

Применяются стандартные миграции Laravel для пользователей, сессий, кеша и очередей, а также для журнала счётчиков и показаний. Справочник аварийных инструкций хранится в конфигурации. Личные записи счётчиков пока не синхронизируются с поставщиками и ГИС ЖКХ. PostgreSQL хранит данные в томе `umka_sail-pgsql`; `DatabaseSeeder` заполняет синтетический пилот в local/testing. Дополнительные таблицы хранят дома, членство, проблемы, ответы и журналы действий; схема дома и привязки этажей задаются администратором.

Материалы «Умный город» использованы как контекст продукта. Рекомендованный в материалах React заменён на Vue по явному выбору пользователя. Для реального запуска внутри MAX ещё нужно подключить бот и проверить приложение в платформе.

Официальная документация: [Laravel 13](https://laravel.com/docs/13.x), [Inertia 3](https://inertiajs.com/docs/v3/installation/client-side-setup), [Laravel Sail](https://laravel.com/docs/13.x/sail).

### Приглашения жителей

Администратор дома открывает «Управлять участниками» → «Пригласить жителя», задаёт квартиру и при наличии схемы подъезд/этаж. Одноразовый код действует 72 часа, хранится только в виде хеша и показывается при создании. Его можно отозвать в том же разделе. Код передаётся лично после проверки адреса; он даёт только роль жителя и не подтверждает право собственности.

Житель входит через MAX, открывает «Проблемы в доме» → «Вступить по приглашению», вводит код, проверяет дом/квартиру и подтверждает вступление. Если задан `MAX_BOT_USERNAME` (имя без `@`), администратор получает ссылку `https://max.ru/<bot>?startapp=invite_<code>`: она подставляет код после авторизации, но не принимает приглашение автоматически. Без имени бота доступен ручной ввод. Истёкшие/отозванные/использованные приглашения и приглашения бывшего администратора не дают доступ; уже существующая роль не меняется. Выдача, отзыв и принятие фиксируются в журнале.

### Уведомления и адресные опросы MAX

Житель включает согласие отдельно для каждого дома в разделе «Проблемы в доме» и начинает диалог с ботом в MAX. По умолчанию уведомления выключены. Диспетчер открывает «Опросы и доставка MAX» в карточке проблемы, выбирает подъезд и диапазон этажей. В очередь попадают только согласившиеся жители этого участка без свежего ответа. Повторный запуск не дублирует действующий опрос. После завершения работ автоматически создаются запросы проверки восстановления для заявивших о проблеме жителей; изменения плана работ также уведомляют подписанных заявителей.

Вопрос содержит три кнопки. Ответы боту и мини-приложению используют общие правила доступа и запись ответов. Проверяются отправитель MAX, членство, согласие, расположение и текущий раунд; старые кнопки не подтверждают новый раунд работ. Повторная доставка одного callback не обновляет время ответа. Остановка бота отключает согласие. Статус «отправлено» означает подтверждение API MAX, а не прочтение жителем.

Настройка на сервере:

1. Задать локально `MAX_BOT_TOKEN`, `MAX_BOT_USERNAME`, `MAX_WEBHOOK_URL=https://<домен>/api/max/webhook` и случайный `MAX_WEBHOOK_SECRET` (5–256 символов A–Z, a–z, 0–9, `_`, `-`). Секреты не коммитить. Webhook требует публичного HTTPS на порту 443 с доверенным сертификатом.
2. Выполнить миграции: `./vendor/bin/sail artisan migrate --force`.
3. Явно зарегистрировать webhook: `./vendor/bin/sail artisan max:subscribe-webhook`. Команда подписывает на `message_callback` и `bot_stopped`; при запуске приложения подписка сама не создаётся.
4. Запустить Laravel scheduler (`artisan schedule:work` для разработки; `artisan schedule:run` каждую минуту на сервере). Он вызывает `max:send-notifications`. Для разового запуска: `./vendor/bin/sail artisan max:send-notifications --limit=30`. Нужен общий cache store для блокировки отправителя при нескольких процессах; штатный database cache подходит.

Очередь сохраняется в БД, отправка ограничена одним сообщением в секунду. При HTTP 429/5xx выполняется до пяти попыток с задержкой; ошибки авторизации и другие 4xx завершают доставку. Тайм-аут, неоднозначный успешный ответ или прерванный worker отмечаются как `uncertain` и автоматически не повторяются: API не даёт ключа идемпотентности, и сообщение могло дойти. Callback от получателя подтверждает такую доставку. Диспетчер видит сводку доставки; при неопределённом результате проверяют журнал бота и конфигурацию перед новой рассылкой. Просроченные, отозванные или более не актуальные сообщения отменяются. Квитанции callback очищаются через семь дней, срок действия вопросов — `INCIDENT_RESPONSE_FRESHNESS_HOURS`.

Транспорт проверяется тестами с подменой внешнего HTTP. Настоящая доставка и работа кнопок в мобильном/веб-клиенте MAX требуют проверки с подключённым ботом. Для локальной проверки ответы реальным жителям не отправлялись.

Официальные контракты: [отправка сообщений](https://dev.max.ru/docs-api/methods/POST/messages), [webhook](https://dev.max.ru/docs-api/methods/POST/subscriptions), [кнопки](https://dev.max.ru/docs-api/use-cases/sending-messages/keyboard), [ответ на callback](https://dev.max.ru/docs-api/methods/POST/answers). Используется домен `platform-api2.max.ru`, токен передаётся заголовком `Authorization`; webhook проверяет `X-Max-Bot-Api-Secret`.
